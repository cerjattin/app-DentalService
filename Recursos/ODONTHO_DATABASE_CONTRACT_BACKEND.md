# ODONTHO SERVICES — SVB BILLING APP
## DATABASE CONTRACT — Backend Handoff
**Database:** MySQL 8  
**ORM:** Prisma 7  
**Database name:** `odontho_svb_billing`  
**Organization timezone:** `America/Curacao`  
**Status:** Database baseline validated for Backend implementation

---

## 1. Purpose

This document is the authoritative database contract between the ODONTHO database layer and the Backend/API.

The Backend MUST respect the business invariants, historical immutability rules, transaction boundaries and identifier semantics described here.

The database models the business domain. CSV, TXT, XLSX, JSON, XML and SVB API payloads are generated by adapters from the domain model and MUST NOT drive the database structure.

## 3. Identifier contract

### Internal primary keys

All core entity IDs use MySQL `BIGINT UNSIGNED`.

Prisma exposes them as JavaScript `bigint`.

API responses MUST serialize IDs as strings.

Example:

```json
{
  "id": "1542",
  "patientId": "850"
}
```

DO NOT cast database BigInt IDs to JavaScript `number`.

### Business identifiers

Business identifiers are separate from primary keys.

Examples:

- `patient_number`
- `appointment_number`
- `invoice_number`
- `declaration_number`
- `detail_invoice_number`
- `insured_id`
- SVB `provider_id`
- SVB `authorization_id`

Backend MUST NOT derive a business number from the primary key.

---

## 4. Monetary contract

Financial values use exact decimals.

Backend MUST use Prisma `Decimal` / decimal-safe handling and MUST NOT use floating-point arithmetic for financial totals.

Important fields include:

- `svb_tariffs.amount`
- `encounter_procedures.unit_tariff_snapshot`
- `encounter_procedures.amount`
- `invoice_versions.total_amount`
- `invoice_items.unit_tariff_snapshot`
- `invoice_items.amount`
- `declaration_items.amount_snapshot`

Standard formula:

```text
amount = unit_tariff × quantity
```

The Backend MUST validate the formula before locking historical records.

## 7. Organization and providers

### Organization

`organizations` represents the declaring/legal entity.

SVB `DeclarantId` belongs to the organization.

`declarant_id` may initially be NULL until the real SVB identifier is configured.

### Clinic location

`clinic_locations` represents the physical service site/policlinic.

SVB `PoliClinic` is derived from `policlinic_code` and later frozen into snapshots.

### Provider

`providers` is separate from `users`.

A provider can exist without a login account.

For SVB billing the provider requires a valid `svb_provider_id`.

Historical billing MUST use provider ID snapshots rather than reading the current provider master.

---

## 8. Patient and insurance

`patients` represents the person.

`patient_insurance` represents a coverage period.

SVB `InsuredId` belongs to `patient_insurance`, not directly to `patients`.

Relationship:

```text
Patient 1:N PatientInsurance
Payer   1:N PatientInsurance
```

The active insurance used in billing MUST belong to the same patient as the appointment/invoice.

The Backend MUST reject overlapping equivalent insurance periods.

---

## 9. Appointment contract

An appointment belongs to:

- one organization
- one patient
- one provider
- one clinic location
- one date/time interval

A patient appointment can optionally reference:

- a treatment case
- an accident case

Core rule:

```text
scheduled_end_at > scheduled_start_at
```

Backend MUST prevent overlapping appointments for the same provider when neither appointment is `CANCELLED` nor `NO_SHOW`.

### Appointment states

```text
SCHEDULED
CONFIRMED
CHECKED_IN
IN_PROGRESS
COMPLETED
CANCELLED
NO_SHOW
```

Every business state transition MUST append an `appointment_status_history` record.

Appointments with downstream clinical/billing history MUST NOT be physically deleted.

---

## 10. Clinical encounter contract

Relationship:

```text
Appointment 1 : 0..1 ClinicalEncounter
```

`clinical_encounters.appointment_id` is UNIQUE.

Therefore a single appointment has at most one clinical encounter.

States:

```text
OPEN
COMPLETED
VOID
```

A completed encounter requires `completed_at`.

Backend MUST NOT create/close a bill from an OPEN encounter.

---

## 11. Diagnosis contract

Master:

```text
diagnosis_codes
```

Applied diagnosis:

```text
encounter_diagnoses
```

An encounter can contain multiple diagnoses but at most one primary diagnosis.

The database does not fully enforce this conditional rule; Backend MUST enforce it transactionally.

Applied diagnoses preserve code/description snapshots.

An `EncounterProcedure.diagnosisId`, when used, MUST point to a diagnosis from the same clinical encounter.

---

## 12. SVB procedure and tariff contract

Master tables:

- `svb_procedures`
- `svb_tariffs`

Tariffs are temporal.

Backend MUST select the tariff valid for the service date.

Equivalent tariff periods for the same procedure/currency MUST NOT overlap.

Do not overwrite a historical tariff to introduce a new rate.

Create a new tariff period instead.

## 13. Authorization contract

Tables:

- `svb_authorizations`
- `svb_authorization_items`

An authorization belongs to:

- one patient
- one patient insurance record

An authorization item may cover a specific SVB procedure and authorized quantity.

Backend MUST verify:

- correct patient
- correct insurance
- authorization status
- validity dates
- applicable procedure
- remaining quantity

`used_quantity` is operational state, but historical consumption MUST remain reconstructable from procedures that reference authorization items.

- diagnostic code
- treatment ID

```text
PLANNED
```

## 15. Central appointment → invoice invariant

This is a mandatory project rule.

```text
1 Appointment
    ↓
0..1 ClinicalEncounter
    ↓
1..N EncounterProcedures
    ↓
0..1 logical Invoice
    ↓
1..N InvoiceVersions
    ↓
1..N InvoiceItems per version
```

A single appointment may contain multiple procedures.

All billable procedures from the same appointment form ONE logical invoice.

`invoices.appointment_id` is UNIQUE.

Backend MUST NEVER create one invoice per procedure.

Relationship:

```text
Invoice 1:N InvoiceVersion
```

Unique:

```text

```

Types:

```text
ORIGINAL
CORRECTION
```

Version states:

```text
DRAFT
PENDING_SIGNATURE
SIGNED
CLOSED
SUPERSEDED

```

### Historical immutability

A version in:

```text
SIGNED
CLOSED
SUPERSEDED
```

MUST NOT be edited destructively.

Backend services MUST reject direct mutations of locked versions.

Corrections create a new version.

## 18. Invoice item contract

Invoice items belong to an invoice version.

Relationship:

```text
InvoiceVersion 1:N InvoiceItem
```

Unique line number:

```text
(invoice_version_id, line_number)
```

Normally:

```text
1 performed procedure

1 invoice item per invoice version
```

An item MUST originate from a performed procedure belonging to the same appointment as the logical invoice.

Invoice item snapshots are the canonical source for historical billing.

## 20. Invoice number allocation

Number allocation MUST use `number_sequences`.

Never use:

```text
MAX(invoice_number) + 1
```

Unique sequence identity:

```text
organization_id
sequence_type
sequence_year
```

Supported sequence types:

```text
PATIENT
APPOINTMENT
INVOICE
DECLARATION
```

Correct algorithm:

```text
BEGIN
  UPDATE number_sequences
     SET current_value = current_value + 1
   WHERE organization/type/year = target

  READ updated row

  format business number

  create/update target business record
COMMIT
```

The allocation and the business operation MUST be in the same transaction.

Concurrency test baseline:

- 50 concurrent requests
- 50 unique results
- 0 duplicates
- contiguous test values
- final counter = 50

## 21. Preparing an invoice for signature

This is a critical transaction.

Preconditions:

- appointment exists
- clinical encounter is COMPLETED
- at least one billable `PERFORMED` procedure
- correct patient
- valid patient insurance
- provider has SVB Provider ID
- required authorization valid
- required diagnosis available
- tariff valid for service date
- procedure amounts valid

Transaction:

```text
BEGIN

1. lock/load invoice aggregate
2. allocate InvoiceNumber if not yet assigned
3. build invoice version
4. copy all billable procedures into invoice_items
5. assign line/detail numbers
6. compute and validate total
7. freeze patient/insured/declarant/provider/procedure snapshots
8. create canonical content representation
9. compute SHA-256 content_hash
10. set version PENDING_SIGNATURE + locked_at
11. set invoice PENDING_SIGNATURE
12. write invoice_status_history
13. write audit_log

COMMIT
```

If any step fails: ROLLBACK.

## 22. Signature contract

The signature belongs to a specific `invoice_version`.

It MUST NOT belong merely to the logical invoice.

Files are stored outside MySQL.

Database stores:

- document reference
- resource hash
- signed content hash
- signature type
- signer
- capture method
- timestamp
- capture user
- technical metadata

For a VALID signature:

```text
signature.signed_content_hash
=
invoice_version.content_hash
```

A corrected invoice version requires a new signature.

A signature from version 1 MUST NOT silently authorize version 2.

---

## 23. Closing an invoice

Preconditions:

- version status = SIGNED
- VALID signature exists
- signature hash matches version content hash
- total equals item sum
- required snapshots complete

Transaction:

```text
BEGIN
  validate version
  validate signature
  validate total
  set version CLOSED + closed_at
  set logical invoice CLOSED
  append status history
  append audit log
COMMIT
```

Closed content is immutable.

## 24. Correction contract

Table:

```text
invoice_corrections
```

Correction always references a source version.

Flow:

```text
source version
    ↓
correction REQUESTED
    ↓
APPROVED
    ↓
new InvoiceVersion type CORRECTION
    ↓
new signature process
    ↓
new version CLOSED
    ↓
old version SUPERSEDED
    ↓
correction APPLIED
```

The original version and original invoice items MUST remain unchanged.

`source_version_id` and `replacement_version_id` MUST belong to the same logical invoice as the correction.

## 27. Declaration snapshot contract

`declaration_items` freezes the SVB submission row.


## 29. Delete contract

Historical records MUST NOT be cascade-deleted.

Normal business operations MUST NOT physically delete:

- appointments with history
- clinical encounters
- performed procedures used in billing
- invoice versions
- invoice items
- signatures
- historical documents
- invoice corrections
- declaration batches/items/exports/submissions
- audit logs

Use business states such as:

- inactive
- archived
- cancelled
- void
- superseded

FK RESTRICT is intentional.

## 30. Backend-only transactional invariants

The following cannot be fully guaranteed by a simple FK/UNIQUE and MUST be validated transactionally:

1. no provider schedule overlap
2. max one primary diagnosis per encounter
3. patient insurance belongs to appointment patient
4. authorization belongs to correct patient/insurance
5. authorization item applies to procedure
6. selected tariff belongs to selected procedure
7. tariff valid for service date
8. no overlapping equivalent tariff periods
9. no overlapping equivalent insurance periods
10. invoice patient = appointment patient
11. invoice insurance belongs to invoice patient
12. invoice item procedure belongs to same appointment
13. invoice currentVersion belongs to same invoice
14. correction source/replacement versions belong to same invoice
15. source invoice item belongs to same logical invoice
16. signed/closed versions cannot be mutated
17. invoice total = sum(invoice items)
18. valid signature hash = invoice version content hash
19. declaration item belongs to invoice from same organization

These invariants were included in the database consistency audit baseline.

## 38. Golden rule for Backend

If a record participates in a signed, closed or declared financial history:

> Never silently rewrite history.

Use:

```text
state transition
+
new version/correction when required
+
status history
+
audit event
```

This is the core integrity principle of ODONTHO SERVICES — SVB BILLING APP.
